# Seek backward-snap — root-cause diagnosis (2026-07-16)

Deep-research result: 4 CONFIRMED + 2 PARTIAL mechanisms, each adversarially verified against branch library-home-v2.


## RC1 [CONFIRMED] Duration-authority split + triple-duplicated App-layer clamp

**Mechanism:** Duration-authority split + triple-duplicated App-layer clamp. Every timecode click is clamped to durationFrames-1, where durationFrames derives ONLY from yt-dlp metadata.duration (App.tsx:534-537). Three separate copies of this clamp exist (App.tsx:3653 onSeek, 4255-4258 panel-bus onSeek, 4804-4808 docked drawer onTranscriptSeek). When metadata.duration is null — the deliberate r59 playback-first window seeds a stub with duration:null (App.tsx:1630-1650) and playback starts ~9s before fetch_metadata hydrates; a failed fetch_metadata leaves it null forever (App.tsx:1708-1711 'if this fails we leave the player visible') — durationFrames is 0 and the clamp math (Math.max(0, Math.min(Math.max(0,-1), f)) or Math.max(0, Math.min(-1, f))) sends EVERY click to frame 0. When yt-dlp understates duration, far clicks clamp backward to the understated end. The player's own knownDuration guard (MSEStreamPlayer.tsx:178-183, added in f483e30 after '19:40 landed at 15:12') sits BELOW these App clamps and cannot rescue a target already destroyed in frames. onReady(total) fires with total=0 on the r79 fast path when metadata is late (MSEStreamPlayer.tsx:507,577-580) and App's fill is gated on dur>0 (App.tsx:1484), so nothing else backfills the duration.

**Evidence:** App.tsx:3653 `Math.max(0, Math.min(Math.max(0, durationFrames - 1), f))`; App.tsx:4255-4258 and 4804-4807 `Math.max(0, Math.min(durationFrames - 1, Math.floor(seconds*r)))`; App.tsx:534-537 durationFrames from metadata?.duration else 0; App.tsx:1632 stub `duration: null`; App.tsx:1484 `if (dur > 0)` gate on onPlayerReady's fill; MSEStreamPlayer.tsx:90-93 + 178-190 record the prior '19:40 → 15:12' incident and ship a diagnostic for exactly this clamp — instrumentation that only exists because the symptom recurred. Long-form sources have the slowest metadata fetches, so this fires most on exactly the reported content type.

**User-visible:** Clicking a transcript cue, chapter, or timeline position lands the playhead at 0:00 (metadata not yet hydrated / fetch failed) or at an earlier time than clicked (understated duration). The literal 'playhead moves itself back' numeric snap.

**Verifier:** Every load-bearing citation checks out against the actual code. (1) App.tsx:534-537: durationFrames = floor(metadata.duration * round(fps)) when metadata?.duration != null, else 0. (2) Three duplicated clamps confirmed: App.tsx:3653 onSeek `Math.max(0, Math.min(Math.max(0, durationFrames - 1), f))`; App.tsx:4255-4258 panel-bus onSeek and App.tsx:4804-4807 docked-drawer onTranscriptSeek, both `Math.max(0, Math.min(durationFrames - 1, Math.floor(seconds * r)))` feeding onSeek. With durationFrames === 0 all three provably reduce every click to frame 0: min(max(0,-1), f)=0 and max(0, min(-1, x))=0. onSeek then calls publishPlayheadFrames(0) — the visible backward snap — and seekTo(0), which rebuilds the stream at 0. (3) The r59 playback-first stub (App.tsx:1630-1649) seeds duration: null and kicks playback off in parallel (loadWebPlayback, line 1705) before fetch_metadata resolves; on fetch_metadata failure (catch at ~1755, matching the quoted 1708-1710 comment 'If this fails we leave the player visible') the player stays up and NO code path ever writes duration afterward — the only duration writes in App.tsx are setMetadata(m) at 1717 (the fetch that failed) and the onPlayerReady fill at 1484-1490, which is gated `if (dur > 0)`. (4) MSEStreamPlayer.tsx:494-509 (r79 fast path, the normal YouTube path since the resolver targets H.264): totalDurationRef.current = knownDurationRef.current, which is 0 while metadata is absent (knownDuration prop = metadata?.duration, Monitor.tsx:437); onReady(total) at 577-580 therefore fires with 0, so the dur>0 gate leaves durationFrames stuck at 0. (5) MSEStreamPlayer.tsx:90-93 and 175-190: the knownDurationRef guard, the '19:40 landing at 15:12' incident comment, and the seek diagnostic all exist verbatim — and seekTo receives `clamped / r`, i.e., seconds already destroyed by the App-layer clamp, so the player-level guard structurally cannot rescue it (the prior fix landed one layer too low, which is exactly why the bug can recur above it). Walkable sequence: paste long YouTube URL → stub duration:null → stream plays → fetch_metadata fails (classic yt-dlp bot-check/cookie failure; app deliberately keeps playing) → user loads/generates a transcript → clicks cue at T → drawer clamp min(-1, floor(T*r)) → 0 → playhead shows 0:00 < T. The understated-duration variant (clamp to durationFrames-1 below the clicked time) follows from the same lines. The 'recurs because' story also holds structurally: the clamp is triple-duplicated in App while the authoritative-duration guard lives only inside the player, below the destruction point.


## RC2 [CONFIRMED] Keyframe-preceding ffmpeg -ss with an asserted (not measured) baseTime — fires on essentially every click on long-form

**Mechanism:** Keyframe-preceding ffmpeg -ss with an asserted (not measured) baseTime — fires on essentially every click on long-form. The proxy's /fmp4 route puts -ss BEFORE -i with -c copy (stream_proxy.rs:402-412), so the delivered stream actually starts at the nearest keyframe K AT-OR-BEFORE the requested T (up to a full GOP, several seconds on YouTube VODs). -avoid_negative_ts make_zero (stream_proxy.rs:425) rebases the earliest sample (K, not T) to PTS 0, and ffmpeg's actual landing point is destroyed (stderr nulled at :438, no response header). The frontend then ASSERTS baseTime = requested T (MSEStreamPlayer.tsx:248) and clockOrigin = buffered.start(0) (:570-572), so on muxed sources the reported playhead reads T while the audible/visible content plays from K — up to a GOP earlier. The transcript karaoke highlight follows the asserted number, so what you hear is BEHIND where you clicked: experienced as 'it snapped back / didn't stick'. On DASH-split sources (two -ss inputs, :402/:408) the audio track seeks ~frame-accurately, so buffered.start(0) ≈ T−K absorbs the gap by accident — meaning a fix validated on one path silently regresses the other. Long-form funnels ~every click into this rebuild path: BUFFER_AHEAD_SECONDS=30 (:69) plus QuotaExceeded eviction to currentTime−10 (:444-449) leave a ~40s in-buffer window on a multi-hour timeline, so the in-buffer fast path (:227-238) almost never matches.

**Evidence:** stream_proxy.rs:399-412 (input-side -ss + -c copy; comment claims 'keyframe-accurate' — it is keyframe-PRECEDING), :425-427 (make_zero single-shift rebase), :438 (stderr → null), :459-468 (no start-time header); MSEStreamPlayer.tsx:243-252 (baseTime := requested t), :598 (sourceopen publishes baseTime as the playhead), :706-707 (corrected() maps local→T+elapsed). The fossil record of misattributed fixes: e779d5f shipped a user-facing ±15s caption-offset slider; 505616d/1d46f70 added the audio-twin clock twice; cd11f08/216b3ae removed it twice — all chasing displacement whose origin is this proxy-side keyframe snap.

**User-visible:** After clicking a cue on a long-form source, the timecode readout shows the clicked time but the video/audio play content from up to several seconds BEFORE it; the karaoke highlight and captions mismatch what is heard. Reads as 'the playhead went back / the click didn't take'.

## RC3 [CONFIRMED] Co-review host chase deterministically reverts local seeks

**Mechanism:** Co-review host chase deterministically reverts local seeks. While a session is live and the host is playing, every 500ms transport heartbeat compares the local playhead against the host's extrapolated position and calls onSeek(host position) whenever drift > 0.5s — with no 'local seek in flight' suppression, no recent-gesture latch, and no pending-target comparison. A guest clicking a transcript cue 40 minutes ahead is yanked back within one heartbeat. While paused, the hostScrubbed branch reverts any local move > 0.1s whenever the host position shifted.

**Evidence:** use-co-review.ts:186-196: `const cur = getPlayheadFrames()/r; … if (m.playing) { if (Math.abs(cur - expected) > 0.5) onSeek(Math.floor(expected * r)); } else if (justLoaded || (hostScrubbed && Math.abs(cur - expected) > 0.1)) onSeek(…)`. The comment at :190-192 shows the paused case was already softened once (573123f) because of yank complaints — the playing case never was. This mechanism has nothing to do with the MSE pipeline, so pipeline fixes can never remove it.

**User-visible:** During a co-review session with the host playing (or after the host scrubs while paused), any timecode click by a guest visibly snaps back to the host's position within ~0.5s — a deterministic, reproducible 'playhead moves itself back'.

**Verifier:** Every factual assertion in the claim checks out against the actual code. (1) The chase logic is at src/hooks/use-co-review.ts lines 186-196 exactly as quoted: `expected = m.position + (m.playing ? elapsed*rate : 0)` (l.186), `cur = getPlayheadFrames()/r` (l.187), and l.193-194 `if (m.playing) { if (Math.abs(cur - expected) > 0.5) onSeek(Math.floor(expected * r)); }`. (2) The heartbeat is a 500ms setInterval on the host (l.264). (3) There is genuinely no suppression: onSeek (App.tsx:3650-3656) just publishes playhead frames and calls playerRef.seekTo — no 'local seek in flight' flag, no recent-gesture latch, no pending-target comparison anywhere in the handler or App-side seek path. A guest clicking a transcript cue (App.tsx:4251-4259 → onSeek) publishes the new playhead synchronously, so the very next heartbeat (≤500ms) sees drift ≫0.5s and calls onSeek(host position) — deterministic yank-back. (4) Routing verified in src-tauri/src/commands/session.rs: session_broadcast goes only to peers and peers emit session:msg from their read loop (l.589); the host never receives its own transport, and only the host sends transport — so the chase affects guests only, as the claim implies. (5) The paused branch (l.195) reverts local moves >0.1s when hostScrubbed (host position shifted >0.25s between heartbeats, l.188) or on justLoaded. (6) The comment at l.190-192 confirms the paused case was deliberately softened ('so a paused guest can glance at a nearby frame without being yanked back on every heartbeat') while the playing case was not; commit 573123f exists and is the session-first/snap-on-load ready-gating work. (7) The mechanism is entirely outside MSEStreamPlayer — MSE pipeline fixes cannot remove it. Bonus: a far out-of-buffer seek doesn't even escape via readiness — MSEStreamPlayer's readyRef only resets on path change/dispose (MSEStreamPlayer.tsx:357, 669), so isReady() stays true through a rebuild and the chase fires; and if it did flip false, the justLoaded branch (l.183, 195) snaps to the host anyway.

## RC5 [PARTIAL] Rebuild-window race holes inside MSEStreamPlayer

**Mechanism:** Rebuild-window race holes inside MSEStreamPlayer. (a) The 280ms rebuild timer nulls pendingSeekRef BEFORE the multi-second rebuild completes (MSEStreamPlayer.tsx:243-252), so getCurrentTime's 'report the target while seeking' guard (:256-257, requires pendingSeekRef != null) is disarmed for the whole rebuild and falls through to NEW baseTime + (OLD element currentTime − OLD clockOrigin) — a hybrid garbage value; seekBySeconds (←/→) seeds its target from it (App.tsx:3544) and republishes/clamps it. clockOriginRef is never reset at teardown, only recaptured at the new pipeline's first updateend (:564,:570-573). (b) A second click T2 landing between the T1 debounce firing and T1's sourceopen: sourceopen (gen still current — gen only bumps at teardown) unconditionally clears seekingRef, publishes onTimeUpdate(baseTime = T1), and consumes wantPlayRef (:597-603) — visibly snapping the just-published T2 back to T1 and resuming the wrong stream for ~280ms until T2's timer tears it down. (c) The 300ms settle timer vs the 280ms rebuild timer: correctness of seekingRef currently depends on sourceopen's unconditional clear — a hand-maintained ordering, not an invariant.

**Evidence:** MSEStreamPlayer.tsx:243-252 (pendingSeekRef.current = null before teardown+rebuild), :256-261 (guard requires pendingSeekRef != null), :212-220 (settle bails on !sbRef leaving seekingRef=true), :556-604 (sourceopen: seekingRef=false; onTimeUpdate(baseTimeRef.current); wantPlay consumed — no pendingSeekRef/rebuildTimerRef check). App.tsx:3540-3548 (seekBySeconds reads p.getCurrentTime()).

**User-visible:** Pressing arrow keys or making a second click during the seconds-long rebuild after a timecode click lands the playhead at a position derived from a stale clock (often earlier); rapid double-clicks briefly snap back to the first target and can land paused.

**Verifier:** Sub-claim (a) does not hold: getCurrentTime during a rebuild reports the correct target, not a hybrid stale-clock value. Three cooperating facts the claim missed: (1) baseTimeRef.current = t is assigned at MSEStreamPlayer.tsx:248 BEFORE teardown, so the fallthrough's base term is already the target; (2) on rebuilds mimeRef.current is cached, so buildPipeline has no await before video.src = objectUrl (:554) — the element's currentTime resets to ~0 within the same task the timer runs in, leaving no cross-task window where OLD currentTime is readable; (3) the Math.max(0, raw − clockOrigin) clamp (:260, :707) makes the stale clockOriginRef harmless while currentTime is 0 (it IS never reset at teardown — that detail is correct — but it's recaptured at the new pipeline's first updateend before currentTime can advance). Arrow keys during a rebuild therefore seed from the right position; any residual error would be forward, not the reported backward snap. Sub-claim (b) IS a genuine defect (sourceopen at :597-603 unconditionally clears seekingRef, republishes baseTime=T1, and consumes wantPlayRef with no pendingSeekRef/rebuildTimerRef guard), but its window is only the tens of milliseconds between the T1 debounce firing and T1's MediaSource sourceopen, and it self-corrects ~280ms later — it explains brief double-click snap-backs and landing paused, not a persistent single-click backward snap. Sub-claim (c) is a fair fragility observation (280ms rebuild vs 300ms settle ordering is hand-maintained), not an independent failure.


## RC6 [PARTIAL] fps flip reinterprets the frames-canonical playhead store

**Mechanism:** fps flip reinterprets the frames-canonical playhead store. The store is canonical in integer frames at the CURRENT fps (playhead-store.ts:16-22, 64-66), and fps silently flips from fallbackFps to metadata.fps when yt-dlp metadata hydrates mid-playback (App.tsx:533; the stub has fps:null). Frames published at the old fps are re-read at the new fps, shifting every displayed clock (timecode, timeline cursor, karaoke highlight) backward by the ratio (e.g. −20% for 24→30). It self-corrects only on the next player tick (App.tsx:1448-1451), but every seek pauses playback (MSEStreamPlayer.tsx:203) and 'timeupdate' doesn't tick while paused, so the wrong value persists exactly when the user just clicked. Additionally, every click round-trips seconds→floor(frames)→seconds across three conversions, landing up to one frame before the clicked cue.start by construction.

**Evidence:** App.tsx:533 `fps = metadata?.fps && metadata.fps > 0 ? metadata.fps : fallbackFps`; App.tsx:1643 stub `fps: null`; playhead-store.ts:64-66 (frames/round(fps) at read time); App.tsx:1448-1451 (self-correction only on a tick); MSEStreamPlayer.tsx:203 (seek pauses playback for the gesture).

**User-visible:** If metadata hydrates during the playback-first window while paused after a click, all clocks jump backward proportionally to the fps ratio and stay wrong until playback resumes — a visible backward shift the user did not cause.

**Verifier:** The fps-flip mechanism is real, unguarded, and all cited lines check out, but three details need correction. (a) "every seek pauses playback and 'timeupdate' doesn't tick while paused, so the wrong value persists exactly when the user just clicked" is overstated: the pause is transient — seekTo's settle timer (MSEStreamPlayer.tsx:211-220) resumes playback ~300ms after the gesture if the video WAS playing (wantPlayRef), and out-of-buffer rebuilds resume via onReady; once playing, the rVFC/rAF tick (MSEStreamPlayer.tsx:708-731) republishes at the new fps and the shift self-corrects within a frame. The wrong value persists only if the video was already paused at click time. Also, 'timeupdate' DOES fire while paused when a seek lands — the code relies on this (MSEStreamPlayer.tsx:738-740: "'timeupdate' stays as the playhead signal while PAUSED — e.g. a seek landing") — so a currentTime change while paused re-corrects too; persistence requires no currentTime change after the fps flip. (b) The seconds→floor(frames)→seconds round-trip is confirmed (App.tsx:4800-4808) but is at most ONE frame (~33-42ms) and the previously user-visible consequence (highlight snapping to the previous cue) is already guarded by the one-frame eps tolerance in TranscriptViewer.tsx:313-332 — it cannot produce the reported visible backward snap on its own. (c) Scope: the fps flip window exists exactly once per source (stub fps:null at App.tsx:1643 until setMetadata at 1717, typically 1-9s after fetch), so this mechanism explains a backward jump only for clicks made during that early hydration window; it cannot explain backward snaps on timecode clicks made minutes into a long-form session, i.e. it is a real contributing bug but not the recurring headline regression. Note it is display-only: the store frames and the actual media position never move — only their seconds interpretation shifts (though a subsequent frame-step at App.tsx:3525-3538 would convert the misread into a real backward media seek).


## Why it keeps recurring
One user-visible invariant — 'the playhead lands at the clicked time and stays there' — is not owned by any single piece of code; it is an emergent agreement smeared across (1) THREE coordinate systems (absolute source seconds; pipeline-local fMP4 seconds offset by baseTime AND clockOrigin; integer frames at a MUTABLE fps), (2) two-to-three duration authorities (yt-dlp metadata vs mediabunny probe vs element duration) guarding the same gesture in different layers, (3) correction math inlined as raw ref arithmetic at ~6 call sites inside MSEStreamPlayer (seekTo, getCurrentTime, two shuttle publishes, corrected(), sourceopen) with no toAbsolute()/toLocal() helper, (4) clamp math copy-pasted at three App call sites, (5) ~10 independent playhead writers (player rVFC, seekTo publish, sourceopen publish, shuttle rAF, App's onSeek/onStep/seekBySeconds/goto/resets, co-review chase, panel heartbeat) arbitrated only by hand-maintained latches (seekingRef, pendingSeekRef, wantPlayRef, genRef) and the accidental ordering of two nearly-coincident timers (280ms rebuild vs 300ms settle), and (6) a proxy that DESTROYS the ground truth the frontend needs — ffmpeg's actual seek landing point is discarded (stderr nulled, timeline rebased by make_zero, no response header), forcing the frontend to reconstruct absolute time from assumptions that are wrong by up to a GOP in a path-dependent way (accidentally right on DASH-split, wrong on muxed — so fixing one path regresses the other). Because no automated test exercises the seek path (vitest covers srt/timecode/commands; the e2e harness mocks IPC and never mounts MSE), every pipeline generation (r63 MSE → r75 DASH merge → r79 probe-skip → r82 audio-twin → r88 revert) and every playback-adjacent feature (shuttle twice, co-review, panel, playhead store) re-derives the conversion and the arbitration by hand and reintroduces the symptom through a new door. Each historical fix was a local patch at one call site (knownDurationRef, seekingRef, localTarget, the caption-offset slider, chase softening) rather than a structural seam — the git record shows five distinct mechanisms and ~7 fix events in six weeks, and the shipped seekTo diagnostic that literally instruments 'a total smaller than s clamps target backward' (MSEStreamPlayer.tsx:186-190) is the fossil proof that the team has chased this exact symptom repeatedly without collapsing the class.

## RC7 (2026-07-18): the "absolute timeline" was never absolute — fMP4 muxer re-zeros

**Symptom (field):** scrub to a frame, hit play → the playhead snaps to ~0
and counts up from there while the picture correctly plays the scrubbed
content. Log signature: `base 0.0` + `clockOrigin 0.00` on a pipeline that
was rebuilt from a nonzero start.

**Mechanism:** RC2 assumed `-ss <t> … -copyts` makes the remuxed fMP4 carry
absolute source timestamps. Verified against the bundled ffmpeg 8.1: the
DEMUX side does preserve pts (a `-f matroska` control shows the true
keyframe time), but the fragmented-MP4 muxer subtracts each track's first
dts — first fragment tfdt is 0 regardless of `-copyts`,
`-avoid_negative_ts disabled`, or `+frag_discont` (checked at the box level,
not just via ffprobe). So the player believed `currentTime` was source time
(X-Timeline: absolute) while the element clock was 0-based:

- the absolute landing seek waited for `buffered` to cover the target —
  which a 0-based buffer never does, so it silently never fired;
- paused scrubs still LOOKED perfect (first buffered frame IS the seek
  point content, and the optimistic `pipeline open` publish shows the
  target), masking the lie until play started publishing the 0-based clock.

**Fix:** the subtraction is a constant — the first video dts at the `-ss`
landing keyframe. `serve_fmp4` recovers it with a one-packet ffprobe at the
same seek target (same avformat backward seek → same keyframe), ships it as
`X-Stream-Epoch`, and the player re-adds it via MSE
`SourceBuffer.timestampOffset` before the first append. Buffered time is
now genuinely absolute: the landing seek fires (frame-exact scrubs and
transcript-word clicks, killing the keyframe-gap audio lead for real), and
play-after-scrub continues from the target. Probe failure or HLS falls back
to `X-Timeline: rebased` (asserted-baseTime math): playhead continuity is
kept, landing precision degrades to the keyframe gap. The probe runs after
the ffmpeg spawn so it overlaps ffmpeg's own connection warm-up, and only
on seek rebuilds (`start > 0`) — boot latency is unchanged.

**Guard:** `parse_stream_epoch` unit tests (dts, N/A→pts fallback,
garbage/negative rejection) in `stream_proxy.rs`. The landing seek and
clock math are unchanged from RC2 — they were always correct; the wire
format was lying to them.
